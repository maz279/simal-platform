## 7.3-1 — Server-derived dirty set + data model

- `migrate.sql` B13 block: `publish_approvals` (change_set JSONB, status CHECK
  pending/approved/rejected/expired, decided_by/decided_at/outbox_id, expires_at,
  status index). Applied live (table exists; count assertions updated 26→27 tables).
- `cms.service.js`: `changeKey()` maps the live audit vocabulary (block/policy/
  announcement/testimonial/slide/rollback targets, incl. `content_blocks/entity:id:lang`
  rollback ids) onto normalized domains; `dirtySet()` = cms_* audit rows since the last
  `ssg_build_completed` (publish + approval BOOKKEEPING actions excluded — found by the
  tests: the approval-request audit itself initially polluted the set); `isSensitiveChange`

  pricing/brand-auth/claims/compliance-date rules (7.3-3, on the DIRTY set, never the
  declared entities).
- `publish()` ignores `entities` for classification. Sensitive set + no valid coverage →
  pending `publish_approvals` row + staff notification + **nothing enqueued** +
  `{pending:true, approvalId}` (route returns **202** via `json()`; `ok()` is 200-only).
  Coverage is one-shot against later edits: an approved row counts only when its
  `decided_at >= dirtySet.maxAuditTs`. A pending row for the identical set is reused.
- Both caller-attested approver paths REMOVED (publish's secondApproverEmail block and
  emergencyPublish's reviewer+attestation path — `compliance_officer` was never a valid
  role per the users CHECK).

## 7.3-2 — Approval routes + UI

- `GET /api/cms/publish-approvals?status=`, `POST …/:id/approve`, `POST …/:id/reject`
  behind `cmsAuth`. Rules enforced server-side: requester (any session of the same user,
  case-insensitive) → 403; not-pending → 409; expired → 409 (row marked expired);
  dirty-set drift since request → 409. Approve → `enqueuePublish()` (the ONLY path that
  creates ssg-builder rows) + decided_by/decided_at/outbox_id + audit + notifications.
- Emergency override is **super_admin only**, emits `cms_emergency_override` and notifies
  every active super_admin.
- UI (cms.js v20): publish toast branches on 202 ("Awaiting second approval — request
  apr_… created (erp/pricing). Nothing is published yet."); new **Publish Approvals**
  panel with pending-first table and Approve/Reject actions.
- `authz-matrix.mjs` ROUTES extended with the three endpoints (battery: gate-authz PASS).
