## 7.2-2 — SLA in fractional business days (GOV a11/a42) + escalation

`review.service.js`:
- module-level `businessDaysBetween(from, to)` — GST (UTC+4) day boundaries, weekend
  from `SLA_WEEKEND_DAYS` (default `0` = Sunday only, per a42; Sat half-day pending PM
  confirmation), FRACTIONAL accumulation (no flooring — the v1.1 stepper read 1.9 bd
  as 1 and 36–47.9h never breached).
- `slaState(s, now)` pure/exported: threshold `SLA_BREACH_BD` (default **2** per a11,
  not 1.5); `query_raised` pauses; the LATEST `partner_updated` history entry restarts
  the clock; `summarise(s, now)` now returns `ageBusinessDays` (1 decimal) alongside
  `ageDays`. Found+fixed en route: `.map(summarise)` passed the array INDEX as `now`
  (classic map(parseInt) trap) → queue always reported 0 bd — call site now
  `.map((s) => summarise(s))`.

`server.js`:
- maintenance interval now awaits the async `repos.sessions.reap()`.
- `escalateSlaBreaches(now)`: one email per breached submission ever (dedupe via
  `sla_escalated` audit targets), `SLA_ESCALATION_EMAIL` gate (`.env` =
  ops@simalme.com), 30-min timer (unref'd), exported from `createApp`.

`pg-reporting.mjs` fixture aged 4 → **5 calendar days** (stays > 2 bd across weekends).

**Unit tests** (`test/unit/sla-business-days.test.js`, 10/10 green): fractional values
exact (1.4/1.6/1.9/2.0); Sunday counts 0 (Fri 00:00→Mon 00:00 = 2 bd, Sat 12:00→Mon
12:00 = 1 bd); 2.0 bd breaches / 1.9 does not (the flooring bug); `query_raised` never
breaches; latest `partner_updated` restarts (2 bd after restart breaches while 2.4 bd

**Integration** (`test/batch-jobs.test.js`, own scratch DB): `escalateSlaBreaches` →
